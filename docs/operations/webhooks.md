# Webhook 개발 현황

Webhook 구독 API와 작업자는 로컬에서 개발·검증 중이며 운영 서비스에서 실행되지 않습니다. 기본적으로 API는 비활성 상태입니다. 공개 운영에 필요한 악용 방지 검증이 남아 있으므로 아직 활성화하지 마세요.

웹의 설정 메뉴에서 **시간표 변경 알림 관리**를 열 수 있습니다. 학교 ID는 시간표 검색 API에서 얻은 컴시간 ID입니다. 새 구독을 만든 직후 표시되는 관리 토큰과 관리 링크는 다시 가져올 수 없으므로 안전한 곳에 보관해야 합니다. 관리 링크는 `webhooks.html#id=<id>&token=<token>` 형태의 URL fragment를 사용하여 복사할 수 있습니다. 브라우저로 관리 링크에 접속하면 화면 스크립트가 URL fragment를 읽은 직후 `history.replaceState`로 주소창에서 fragment를 제거합니다. 제거가 실패하면 자동 인증을 중단합니다. 관리 링크나 토큰을 다른 사람과 공유하거나 브라우저 북마크·동기화에 노출하면 제3자에게 구독 관리 권한이 유출될 위험이 있으므로 주의해야 합니다. 화면은 토큰과 Webhook 주소를 브라우저 저장소에 저장하지 않고 메모리에만 유지하며, 잠금 버튼은 입력값과 조회 결과를 지웁니다.

구독 관리 토큰은 생성할 때 한 번만 반환하고 DB에는 SHA-256 해시를 저장합니다. 대상 URL과 서명 키는 발송에 필요하므로 DB에 보관합니다. 새 DB는 가능한 운영체제에서 소유자만 읽고 쓸 수 있는 권한으로 생성하지만, 기존 파일과 상위 디렉터리의 권한은 운영자가 별도로 확인해야 합니다. 백업과 SQLite 보조 파일에도 동일한 보호가 필요합니다.

관리 링크 교체는 브라우저가 암호학적으로 안전한 새 토큰을 미리 생성합니다. 새 링크를 별도로 보관한 뒤 교체를 확정하면 기존 토큰은 폐기되며 알림 조건과 대기열은 유지됩니다. 응답이 끊겨 결과를 알 수 없으면 보관한 새 링크와 기존 링크를 각각 사용해 확인합니다. API를 직접 사용하는 경우에도 안전한 난수 32바이트를 Base64url로 인코딩한 새 토큰을 먼저 보관하고, 기존 토큰으로 인증한 `POST /api/v1/webhooks/{id}/rotate`에 `{"newToken":"..."}`을 전달해야 합니다. 토큰은 요청 본문에 들어가므로 요청 본문을 기록하지 않는 환경에서만 사용하세요.

전송 대상은 현재 Discord와 Google Chat의 정해진 HTTPS 경로만 허용합니다. 리다이렉트와 환경 프록시는 사용하지 않고, 동일 구독과 이벤트 ID는 한 번만 큐에 넣습니다. 숫자형 `Retry-After`가 소수 초이면 올림해 지연을 지키며 최대 1시간으로 제한합니다. 작업자 임대 만료 시 다시 시도하므로 **전송 성공 직후 프로세스가 종료되면 중복 전송될 수 있습니다**. 재시도에는 같은 이벤트 ID를 사용하지만 외부 서비스가 중복을 제거한다는 보장은 없습니다.

로컬 구현에서는 같은 SQLite 파일에 Webhook 저장소가 초기화된 경우, 이력 관측과 해당 학급의 전송 큐 삽입이 한 트랜잭션에서 이루어집니다. 최초 관측은 알림을 만들지 않습니다. 별도 파일에 저장소를 만들면 이력과 연결되지 않습니다.

합성 데이터로만 실험할 때는 기존 이력 DB 경로를 `OPENCIGAN_HISTORY_DB`에 설정하고 `OPENCIGAN_WEBHOOKS_ENABLED=1`을 지정합니다. `POST /api/v1/webhooks`의 JSON 필드는 `school`, `grade`, `class`, `destination`입니다. 응답의 `id`와 일회성 `token`을 보관하고, 조회·삭제 시 `/api/v1/webhooks/{id}`에 `Authorization: Bearer <token>`을 보냅니다. 토큰은 URL이나 로그에 넣지 않습니다. 삭제는 이미 전송 중인 요청을 취소하지 못합니다.

같은 인증 헤더로 `GET /api/v1/webhooks/{id}/deliveries`를 호출하면 최근 최대 50건의 이벤트 ID, 상태, 시도 횟수, 다음 처리 시각(Unix 초), 최종 HTTP 상태를 볼 수 있습니다. 메시지 본문과 전송 대상 주소는 응답하지 않습니다. `pending`은 대기, `leased`는 작업자가 처리 중, `delivered`는 수신 서버가 성공 상태를 반환한 상태, `failed`는 재시도가 중단된 상태입니다.

같은 인증 헤더로 `POST /api/v1/webhooks/{id}/test`를 호출하면 테스트 메시지가 일반 전송 큐에 등록되고 이벤트 ID가 반환됩니다. 이는 즉시 발송 성공을 뜻하지 않으며 작업자가 실행 중이어야 합니다. 상태 조회에서 해당 이벤트를 확인할 수 있습니다. 구독당 테스트 요청은 최소 60초 간격입니다.

구독 관리 화면의 템플릿은 `{school}`, `{grade}`, `{classroom}`, `{date}`, `{period}`, `{type}`, `{before}`, `{after}` 변수를 지원합니다. Discord는 일반 메시지와 임베드를, Google Chat은 일반 메시지를 사용합니다. 샘플 미리보기는 전송하거나 큐에 넣지 않습니다. 저장 이후에 관측된 변경에만 적용되며 이미 대기 중인 메시지는 바뀌지 않습니다. 출력이 제한 길이를 넘으면 기본 메시지를 사용합니다. 템플릿 API와 예시는 OpenAPI 문서를 참고하세요.

`PUT /api/v1/webhooks/{id}`에 `{"filters":{"subject":"수학","weekday":1}}`처럼 보내면 필터 전체를 교체합니다. `subject`·`teacher`는 변경 전이나 후의 부분 문자열, `weekday`는 월~금 1~5, `period`는 1~20, `type`은 `added`·`deleted`·`changed`입니다. 조건은 AND로 결합하며 빈 객체는 모든 변경을 선택합니다. 변경 후 관측에만 적용되고 이미 큐에 있는 알림은 바뀌지 않습니다.

같은 `filters` 안의 `quietHours`에 `{"start":"22:00","end":"07:00"}`을 넣으면 매일 한국 시간 기준 해당 구간에 발송 예정인 변경 알림을 종료 시각까지 미룹니다. 시작과 종료는 서로 달라야 하며 자정을 넘기는 구간도 지원합니다. 설정은 대기 중인 변경 알림에도 적용됩니다. 사용자가 직접 요청한 테스트 알림은 방해 금지 시간을 무시합니다.

예약 알림은 기본적으로 꺼져 있습니다. 격리된 개발 환경에서만 기존 Webhook 설정과 함께 `OPENCIGAN_SCHEDULER_ENABLED=1`을 지정하면 구독별 `schedule` 관리 API를 사용할 수 있습니다. `immediate`는 관측 즉시, `daily_summary`는 지정한 한국 시각까지 관측된 변경을 한 번 요약하고, `subject_prep`은 해당 날짜의 지정 과목 교시를 묶습니다. 준비 알림은 수집 시각이 30분을 넘었거나 응답이 오래됐거나 불완전하면 만들지 않습니다. 시간표 조회는 프로세스 내 캐시와 실패 백오프를 공유합니다.

예약 작업자는 별도 프로세스로 명시적으로 실행해야 하며 알림을 큐에 넣을 뿐 직접 전송하지 않습니다. 운영 서비스나 자동 시작 설정은 제공하지 않습니다. 재시작 시 당일과 방해 금지로 자정을 넘긴 전날의 일정만 확인하며, 그보다 오래된 누락을 소급 발송하지 않습니다. 중복 방지 기록은 최소 31일 보관하고 대기·전송 중 항목은 정리하지 않습니다. 예약을 취소하면 대기 항목과 이후 재시도는 중단되지만 이미 시작된 외부 요청 자체를 회수할 수는 없습니다.

작업자는 같은 환경 변수를 설정한 별도 프로세스에서 `python -m backend.webhook_worker`로 실행합니다. 시스템 서비스는 아직 제공하거나 활성화하지 않습니다. 최초 관측은 기준만 만들며, 이력과 Webhook DB가 같은 파일이어야 합니다. 자동 조회 기능이 없으므로 누군가 시간표를 조회하고 새 원본 데이터가 수집될 때만 변경을 관측합니다.

구독별 대기·발송 중 항목은 최대 1,000건입니다. 꽉 차면 새 알림은 생략하고 구독 조회의 `dropped_events`가 증가하지만 시간표 이력은 유지됩니다. 전송 시도는 최대 6회이며, 완료·실패 항목은 30일 후 작업자 점검 시 정리됩니다. SQLite 파일의 할당 공간은 삭제 직후 자동으로 줄어들지 않을 수 있습니다.

실제 사용 전에는 구독 API 악용 방지, 큐 저장 공간 상한, 작업자 운영, 보관·삭제 및 비밀값 보호를 완성하고 검증해야 합니다.

# 프록시 환경 클라이언트 IP 식별 및 셔터 경계 정책

이 문서는 OpenSigan API의 역방향 프록시(Reverse Proxy) 및 터널(Cloudflare Tunnel, Nginx, Caddy 등) 환경에서 클라이언트 IP 식별 방식, 요청 제한(Rate Limit) 연동, 그리고 서버 과부하 보호 셔터(Shutter)의 우회 경계 정책을 정의합니다. (참조: [알려진 문제 6, 7번](known-issues.md), [운영 가이드](operations.md))

---

## 1. 배경 및 문제 정의

- **알려진 문제 6번 (IP별 요청 제한 오작동 위험):**
  역방향 프록시 뒤에 WSGI 서버(`backend.app`)가 배치될 경우, 소켓 수준의 연결 주소(`REMOTE_ADDR`)는 모두 프록시의 루프백 주소(`127.0.0.1`) 또는 내부 사설망 IP로 인식됩니다.
  - 별도 신뢰 설정 없이 단일 IP로 집계될 경우: 서로 다른 정상 사용자들이 60초당 60회 제한을 공유하여 빈번한 429 Too Many Requests가 발생합니다.
  - 검증 없이 `X-Forwarded-For`를 맹신할 경우: 악의적인 클라이언트가 임의의 IP 헤더를 조작하여 요청 제한을 우회(스푸핑)할 수 있습니다.
- **알려진 문제 7번 (서버 전체 차단 기능 오탐 및 헬스체크 영향):**
  급격한 요청 증가 시 자동 셔터(`backend.shutter`)가 작동하여 전체 요청을 503으로 차단할 때, 프로세스 생존 확인(`status`)이나 모니터링 관리자 엔드포인트까지 차단되면 복구 상태 파악이 불가능해집니다.

---

## 2. 보안 기본값 (Secure Default)

- **기본 동작 (비활성화):**
  신뢰할 수 있는 프록시 설정이 없으면(`OPENCIGAN_TRUSTED_PROXIES` 미지정 또는 빈 값), `X-Forwarded-For` 및 `Forwarded` 헤더를 **완전히 무시**합니다.
- **클라이언트 IP 결정:**
  소켓의 직접 연결 주소인 `REMOTE_ADDR`만 클라이언트 IP로 사용합니다. 이를 통해 외부 직접 연결 환경에서 클라이언트가 헤더를 조작하여 요청 제한을 우회하는 것을 방지합니다.

---

## 3. 신뢰할 수 있는 프록시 CIDR 설정 (Opt-in)

프록시 환경에서 실제 클라이언트 IP를 판별하려면 명시적인 CIDR 구성이 필요합니다.

### 설정 방법

1. **환경 변수:**
   `OPENCIGAN_TRUSTED_PROXIES`에 쉼표로 구분된 실제 프록시의 IP 또는 CIDR 대역을 지정합니다.
   ```bash
   # 로컬 프록시만 사용하는 구성의 예시. 운영 구성을 확인한 후 적용합니다.
   OPENCIGAN_TRUSTED_PROXIES="127.0.0.1/32, ::1/128"
   ```
2. **코드 호출:**
   WSGI 앱 생성 시 `make_app(trusted_proxies="127.0.0.1, 10.0.0.0/8")` 또는 리스트/튜플로 전달할 수 있습니다.
3. **Waitress 연동:**
   `serve()`는 이 환경 변수의 루프백 항목(127.0.0.1·::1)을 Waitress의 `trusted_proxy` 설정에도 반영합니다. Waitress는 자체 신뢰 설정이 없으면 `X-Forwarded-For`를 앱에 전달하지 않으므로, 앱 측 신뢰 목록만으로는 헤더가 도달하지 않습니다. 서버가 루프백에만 바인딩되므로 반영 대상은 루프백 프록시로 한정합니다.

## 4. 헤더 파싱 및 스푸핑 방지 알고리즘

신뢰 프록시 대역이 설정된 경우에도 다음과 같은 안전 규약에 따라 헤더 체인을 검증합니다:

1. **직접 피어(`REMOTE_ADDR`) 신뢰 검증:**
   - `REMOTE_ADDR`가 신뢰 프록시 CIDR 범위에 속하지 않으면, 전달된 모든 헤더를 무시하고 `REMOTE_ADDR`를 클라이언트 IP로 취급합니다.
2. **우측-좌측(Right-to-Left) 체인 탐색:**
   - 체인은 가장 최근에 거친 프록시가 우측에 추가되는 표준 동작을 따릅니다.
   - 체인의 우측 끝부터 역방향으로 이동하며, 신뢰 프록시 대역에 속한 프록시 구간을 건너뜁니다.
   - **가장 먼저 만나는 비신뢰 IP(신뢰 프록시 대역 밖의 IP)**를 실제 클라이언트 IP로 판정하고 탐색을 즉시 종료합니다.
   - 클라이언트가 헤더 앞단에 임의로 주입한 스푸핑 IP(예: `8.8.8.8`)는 평가 대상에서 제외됩니다.
3. **비정상/초과 헤더의 안전한 거부 (Fail-safe):**
   - **길이 및 홉 제한:** 헤더 전체 길이 1,024자 초과 또는 16개 홉 초과 시 헤더 체인을 무효화하고 즉시 `REMOTE_ADDR`로 안전 회귀합니다.
   - **문법 및 IP 유효성:** 정수/문자 혼합, 비정상 IPv4/IPv6 문자열, 빈 홉(콤마 연속)이 포함되어 있으면 체인을 파기하고 `REMOTE_ADDR`로 안전 회귀합니다.
   - **헤더 충돌 방지:** `X-Forwarded-For`와 RFC 7239 `Forwarded`가 동시에 존재할 경우 헤더 밀수(Smuggling) 및 해석 불일치 위험을 방지하기 위해 헤더를 무효화하고 `REMOTE_ADDR`로 회귀합니다.
4. **주소 정규화:**
   - 대괄호 표기(`[::1]`), 포트 번호 결합(`203.0.113.1:8080`), IPv4-mapped IPv6(`::ffff:127.0.0.1`)를 파싱하여 표준 IP 문자열로 정규화합니다.
   - 이를 통해 동일 IP의 다양한 문자열 표기를 이용한 제한 우회를 차단합니다.

## 5. 셔터(Shutter) 과부하 보호 및 우회 경계

`backend.shutter`는 단기 급증 트래픽(기본값: 60초당 600회) 또는 고부하(기본값: 1분 load average 8.0) 감지 시 30초 동안 셔터를 닫아 `503 service_overloaded`와 `Retry-After: 30`을 응답합니다.

### 셔터 우회(Bypass) 경계 및 목적

| 엔드포인트 / 메서드 | 셔터 점검 여부 | 우회 사유 및 목적 |
| --- | --- | --- |
| `GET /api/v1/status` | **우회 (항상 점검 생략)** | 프로세스 생존 확인(Liveness Probe) 및 로드밸런서 헬스체크 정상 유지 목적. 셔터 작동 중에도 200 OK 응답 |
| `GET/HEAD /api/v1/admin/analytics` | **우회 (항상 점검 생략)** | 서비스 과부하 시에도 관리자가 원인을 진단하고 트래픽 통계를 조회할 수 있도록 보장 (자체 Bearer 토큰 인증 필수) |
| `OPTIONS *` (모든 경로) | **우회 (항상 점검 생략)** | 브라우저 CORS 사전 요청(Preflight)은 셔터 영향을 받지 않고 204 No Content 반환. 클라이언트가 적절한 503 상태와 Retry-After 헤더를 읽을 수 있도록 보장 |
| 공개 API (`/schools`, `/timetable`, `/meals` 등) | **점검 대상** | 셔터 닫힘 상태 시 503 반환 및 업스트림 보호 |
| 페이지뷰 수집 (`POST /api/v1/analytics/pageview`) | **점검 대상** | 과부하 상태에서 분석 DB 쓰기 부하를 차단하기 위해 503 반환 |

### 요청 제한(Rate Limit)과의 상호작용

- 셔터 검사는 요청 제한 평가 **이전에** 수행됩니다.
- 셔터가 닫혀 503으로 조기 반환된 요청은 클라이언트의 60회/60초 요청 제한 쿼터를 소모하지 않습니다.
- `/api/v1/status`는 셔터뿐만 아니라 IP별 요청 제한 대상에서도 완전히 제외됩니다.
- **셔터 임계치 유지:** 현재 기본 임계치(600회/60초, 부하 8.0)는 실제 운영 환경 실측 증거 없이 임의 조정하지 않습니다.

## 6. 신뢰 가정 및 한계점 (Limitations)

1. **상위 프록시 신뢰 가정:**
   - 신뢰 목록에 등록된 프록시(Nginx, Cloudflare Tunnel 등)는 외부에서 들어온 요청의 `X-Forwarded-For` 헤더를 적절히 초기화하거나 자신의 수신 IP를 올바르게 우측에 덧붙인다고 가정합니다.
   - 상위 프록시가 헤더를 조작 없이 그대로 통과시키는 설정(Pass-through)인 경우, 최외곽 신뢰 프록시의 설정 점검이 선행되어야 합니다.
2. **사설망 대역 지정 시 경계:**
   - `10.0.0.0/8`, `192.168.0.0/16` 등 넓은 사설 대역을 신뢰 목록에 추가할 경우, 동일 내부망의 다른 비인가 호스트가 프록시인 것처럼 위장하지 못하도록 네트워크 수준의 격리가 보장되어야 합니다.
3. **공유 IP / NAT 환경의 한계:**
   - 학교, 기숙사, 통신사 CGNAT(Carrier-Grade NAT) 등 다수의 사용자가 하나의 공인 IP를 공유하는 환경에서는 해당 공인 IP에 대해 60회/60초 한도가 공동 적용됩니다. 이는 IP 기반 레이트 리미트의 고유한 한계입니다.
4. **비표준 헤더:**
   - `CF-Connecting-IP`, `X-Real-IP`, `True-Client-IP` 등 공급자별 비표준 헤더는 직접 조회하지 않습니다. 역방향 프록시 계층에서 표준 `X-Forwarded-For` 체인으로 매핑하여 전달하도록 권장합니다.

## 7. Workers VPC 원본 IP 서명 전달 (코드 준비, 실제 운영 미검증)

Cloudflare Pages → Private Worker → Workers VPC → Pi 환경에서는 기존 Funnel에서도 루프백을 통해 접근할 수 있습니다. 이때 루프백의 X-Forwarded-For를 신뢰하면 IP 위조 가능성이 있으므로 별도 공유 비밀키로 서명된 IP만 인식합니다.

- Worker는 Cloudflare의 CF-Connecting-IP를 검증하고 X-Opencigan-Client-IP, X-Opencigan-IP-Timestamp, X-Opencigan-IP-Signature를 직접 생성합니다. 외부 요청의 동명 헤더는 전달하지 않습니다.
- HMAC-SHA256의 UTF-8 입력은 METHOD, PATH, RAW_QUERY, IP, UNIX_SECONDS를 각각 LF로 이어 붙입니다. 16진수 소문자 서명을 사용하고 서버는 타임스탬프 ±60초를 허용합니다.
- Pi에 OPENCIGAN_PROXY_IP_SIGNING_KEY가 설정되면 유효한 서명이 있을 때만 해당 IP를 사용합니다. 누락·만료·변조된 경우 소켓 피어 IP로 돌아가고, 기존 X-Forwarded-For / Forwarded는 무시합니다.
- 서명 방식 활성화 시 Waitress의 trusted_proxy 설정을 비활성화하여 X-Forwarded-For가 REMOTE_ADDR를 먼저 덮어쓰지 못하게 합니다. 키를 설정하지 않으면 기존 Waitress/프록시 설정을 유지합니다.
- 서명은 관리자 인증이 아닌 원본 IP 귀속 수단입니다. 요청 전체를 인증하거나 단기 재전송을 차단하는 프로토콜은 아닙니다. 비공개 터널과 서비스 접근 통제를 병행합니다.

### 활성화 및 검증

1. 충분히 무작위인 32바이트 이상의 동일한 비밀키를 Pi의 OPENCIGAN_PROXY_IP_SIGNING_KEY에 먼저 설정하고, Worker의 PROXY_IP_SIGNING_KEY는 Wrangler secret으로 설정합니다. 키를 저장소나 프런트엔드 빌드 변수에 넣지 않습니다.
2. 두 네트워크에서 API를 각각 한 번 호출하여 Pi의 IP별 Rate Limit 및 접속 로그가 실제 공인 IP와 일치하는지 확인합니다. 서명이 깨진 요청과 기존 Funnel 경로의 동작도 검증해야 합니다.
3. 장기 접속 로그는 별도 OPENCIGAN_ACCESS_LOG_DB와 OPENCIGAN_ACCESS_LOG_ADMIN_TOKEN이 있어야 활성화됩니다. 이 작업은 해당 설정·운영 배포를 수행하지 않습니다.
4. 실운영 환경에서 Cloudflare의 CF-Connecting-IP가 Pages Service Binding에 보존되는지, VPC 통신에서 서명 헤더가 전달되는지 검증할 때까지 완료로 표시하지 않습니다.
